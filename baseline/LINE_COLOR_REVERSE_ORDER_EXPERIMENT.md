# `lineColor` 倒序事件实验

日期：2026-08-29（Asia/Shanghai）

状态：已完成。

## 目标

只调查 `lines[].lineColor[]` 的 `time` 不按数组顺序递增时，编辑器如何渲染及保存。本轮不包含同刻事件，不改变 Alpha，也不改变 `judgeRingColor`。

## 现有样例依据

18 个现有 JSON 中共有 3 个 `lineColor` 数组出现时间倒序：

- `Gleam feat. ふわまろ/Chart_IN.json` 第 29 条线：`...164.5, 165, 164.5, 191...`；
- `Pastel Lines/Chart_EZ.json` 第 93 条线：`...165, 166, 167, 168, 165, 166...`；
- 同文件第 94 条线存在相同的 `168→165` 回退。

这些回退段使用了重复颜色，无法仅凭静态文件判断渲染器是否按时间重排、按原数组顺序处理，或只是容忍了冗余数据。因此本实验使用互不相同的颜色。

## 事件设计

所有事件 Alpha 均为 255，且各自 `startColor=endColor`，不会产生事件内部渐变。JSON 数组故意按下列顺序保存：

| 数组顺序 | `time` | 颜色 |
|---:|---:|---|
| 0 | 20 | 红 `(255,0,0,255)` |
| 1 | 26 | 绿 `(0,255,0,255)` |
| 2 | 24 | 蓝 `(0,0,255,255)` |
| 3 | 28 | 黄 `(255,255,0,255)` |

数组时间顺序是 `20、26、24、28`，只有 `26→24` 一处倒序。

如果编辑器渲染前按 `time` 排序，并沿用上一实验确认的旧段右闭规则，则预期为：

```text
t <= 24      红
24 < t <= 26 蓝
26 < t <= 28 绿
t > 28       黄
```

这是“按时间排序”候选结果，不是当前结论。若观察不同，必须按实际颜色记录，不能强行套用该模型。

## 人工观察结果

```text
22 拍：红
24.1 拍附近：红
25.9 拍附近：红
26.1 拍附近：蓝
27 拍：蓝
28.1 拍附近：黄

是否出现渐变：否
是否出现闪烁、消失或报错：否
其他异常：无
已保存并退出：是
```

结果不符合按 `time` 排序后的红→蓝→绿→黄，而是红色保持到越过 26 拍，随后显示蓝色，越过 28 拍后显示黄色。连续播放和指定拍点均没有观察到绿色。

该表现与按原数组顺序扫描相符：

1. 数组第 0 项红色的下一项时间是 26，因此红色保持到 26 拍边界；
2. 第 1 项绿色的下一项时间反而是 24，形成 `26→24` 的负向/空区间，没有取得可观察的正长度显示区间；
3. 第 2 项蓝色虽然自身 `time=24`，但要等数组推进越过前一边界 26 后才显示，并保持到下一项的 28 拍；
4. 越过 28 拍后使用末项黄色。

这是对可见行为的解释模型，不等同于已经定位到内部循环代码。可以确认原数组顺序参与渲染语义，不能确认具体使用了哪一种查找或循环实现。

## 保存结果

- 主保存 SHA-256：`C875CF52C452E960745A385BB6A985E43983F6EC2306BD8D7DE39748D09574FD`；
- 主保存与测试输入字节完全一致；
- 主保存保持时间顺序 `20、26、24、28`，没有自动排序；
- `auto-save 1` 和 `auto-save latest` 也都保持该时间顺序及全部颜色事件。

## 结论

- `lineColor` 渲染不会先按 `time` 自动排序，原数组顺序参与语义：`confirmed`；
- 倒序相邻项可形成没有可观察正长度区间的事件；本轮绿色未显示：`confirmed`（限本测试排列）；
- 倒序后的蓝色事件虽写为 24 拍，却在越过前一数组边界 26 拍后才显示：`confirmed`（限本测试排列）；
- 编辑器可以正常打开、播放和保存倒序数组，没有闪烁、消失、报错或崩溃：`confirmed`；
- 普通保存和自动保存不自动修复或排序该数组：`confirmed`；
- 未来分析、转换和补丁工具不得自动排序颜色事件数组。

异常同刻排列的精确优先级仍未调查。
